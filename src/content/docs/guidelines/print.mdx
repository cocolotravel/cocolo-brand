Roadbooks and proposals are sometimes printed, on **A4**. The same named
document styles switch from screen sizes to point sizes under
`@media print`, read from the token file's print override block.

## A plain document, not the app

A printed roadbook is a **plain document for A4 paper** — not a reduced
copy of the interactive page. No boxes, no fills, no tints: hairline rules
and type carry the whole hierarchy, on a white or transparent background
throughout.

- **Page.** A4, margins 18mm top and bottom, 15mm left and right (set in
  `doc.css`'s `@page` rule — not a literal uniform 15mm). Body text 11pt,
  one column.
- **Type.** Inter and Roslindale, the same families as on screen.
- **No shadows anywhere**, and a card's fill becomes a single hairline rule
  rather than a border box — a pale fill can drift grey or pink on some
  printers, where a plain rule reads reliably in black and white.

### What doesn't print

Because paper can't click or hover: the map, the FAQ blocks, the
Documentation block, action buttons, link-only lines (a database link with
no sentence around it), chevrons, rings, arrows, hotel photos, the
home-tab recap lists, the header bar, the bottom tab bar, the days panel,
modals, "Fin de l'aperçu" end-of-preview markers, and a URL printed after a
link's own text.

### What does

The cover, travellers, the itinerary list, the days, hotels, transports,
services. The emergency numbers print as one plain line on the cover
("Urgences : Police 110 · Ambulance 119") rather than a button or a
coloured bar. "Voucher" prints as plain text, never a tag or a pill.

### Pagination

Each of the five parts — cover, itinerary, hotels, transports, services —
starts on a new page. A heading never ends a page alone: it stays paired
with the block that follows it across the page break.

:::caution[Test print rules in a real browser]
An invalid CSS selector doesn't warn — it silently drops the entire rule.
That's how a solid-navy card and a blank tab went unnoticed for weeks on
the live roadbook. Several orphan-heading and blank-element bugs also only
showed up on a real Chrome print and never reproduced in a headless one —
treat a headless print check as a first pass, not the final one.
:::
